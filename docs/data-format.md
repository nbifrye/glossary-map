## この文書について

この文書は、用語集を保持する中間形式を定めます。形式は JSON Schema の [glossary.schema.json](../schemas/glossary.schema.json) と [term.schema.json](../schemas/term.schema.json) で定義し、JSON Schema で表せない規則はこの文書で定めます。設計上の判断の理由は [設計書](design.md) を参照してください。

## ファイルの構成

用語集ごとに `glossaries/` の下にディレクトリを作ります。ディレクトリ名は用語集の ID と同じにします。

```text
glossaries/
  <用語集の ID>/
    glossary.json
    terms/
      <スラッグ>.json
```

`glossary.json` には用語集の情報を、`terms/` には用語ごとに 1 つの JSON ファイルを置きます。`terms/` には 1 つ以上の用語のファイルを置き、用語のファイル以外は置けません。

各ファイルには、任意で `$schema` を記録できます。値には、そのファイルから JSON Schema のファイルへの相対パスを書きます (例: `terms/` の下のファイルでは `../../../schemas/term.schema.json`)。

この文書で ID と呼ぶ文字列は、小文字の英数字だけから成る語を、ハイフン 1 つずつでつないだものです (例: `example`・`sp800-63-4`)。先頭と末尾にハイフンを置くことや、ハイフンを続けることはできません。また、名前や説明などの文字列には、空白以外の文字を 1 文字以上含めます。

## 用語集

`glossary.json` には、次の項目を記録します。

- `id`: 用語集の ID
- `title`: 用語集の名前
- `source`: 原典の書誌情報。名称 (`name`)・バージョン (`version`)・公開日 (`published`)・URL (`url`)・取得日 (`retrieved`) を記録する。日付は `YYYY`・`YYYY-MM`・`YYYY-MM-DD` のいずれかの形式で、暦の上で存在する日付を書く。URL は、ホストを含む `http://` または `https://` の絶対 URL とする
- `criteria`: 参照と判定する基準の一覧。1 件以上の基準を記録する。基準ごとに、ID (`id`) と説明 (`description`) を記録する。基準の ID は、用語集の中で重複させない

## 用語

用語のファイルには、次の項目を記録します。

- `heading`: 見出し。原典の表記のとおりに記録する
- `slug`: スラッグ。見出しから作ったスラッグを使えない場合に限って記録する (「[スラッグ](#スラッグ)」を参照)
- `headingTranslation`: 見出しの訳文 (`text`) と、見出しのハッシュ値 (`sourceHash`)
- `definitions`: 定義の一覧。1 つの見出しに複数の定義が掲載されている場合は、原典の順に並べる
- `references`: 参照の一覧

### 定義

各定義には、次の項目を記録します。

- `location`: 原典の該当箇所。原典の該当箇所を開ける URL (`url`) と、原典内の記載位置 (`label`、例: 章やページ番号) の少なくとも一方を記録する
- `source`: 定義の原文。後述するブロックの配列で表す
- `translation`: 定義の訳文 (`content`) と、原文のハッシュ値 (`sourceHash`)。訳文も、原文と同じくブロックの配列で表す

原文と訳文には、それぞれ空白以外の文字を 1 文字以上含めます。

### 原文と訳文の構造

原文と訳文は、次のブロックとインラインだけを使った木構造で表します。ブロックとインラインの種類は、`type` の値で区別します。

ブロックには、次の 2 種類があります。

- `paragraph` (段落): インラインの配列 (`children`) を持つ
- `list` (リスト): 番号付きかどうか (`ordered`) と、項目の配列 (`items`) を持つ。各項目はブロックの配列とする

インラインには、次の 3 種類があります。

- `text` (文字列): 空でない文字列 (`value`) を持つ
- `emphasis` (強調): インラインの配列 (`children`) を持つ
- `link` (リンク): URL (`href`) とインラインの配列 (`children`) を持つ。リンクの中には、直接にも強調を介しても、リンクを置けない

たとえば、`A subscriber.` という段落の `subscriber` が強調され、原典の該当箇所にリンクしている場合は、次のように表します。

```json
[
	{
		"type": "paragraph",
		"children": [
			{ "type": "text", "value": "A " },
			{
				"type": "link",
				"href": "https://example.com/glossary#subscriber",
				"children": [
					{
						"type": "emphasis",
						"children": [{ "type": "text", "value": "subscriber" }]
					}
				]
			},
			{ "type": "text", "value": "." }
		]
	}
]
```

リンクの URL には、ホストを含む `http://` または `https://` の絶対 URL だけを使えます。原典のリンクが相対 URL の場合は、取り込みの段階で、原典のページの URL を基準に絶対 URL に変換します。訳文のリンクも同じです。

### 参照

各参照には、次の項目を記録します。

- `definition`: 参照元の定義。`definitions` の 0 から始まる番号で指定する
- `target`: 参照先の用語。用語集の ID (`glossary`) とスラッグ (`term`) の組で指定する。現在は、同じ用語集の用語だけを参照先にできる
- `start`・`end`: 根拠となる表現の原文中の位置
- `text`: 根拠となる表現。原文の `start` から `end` までの文字列と一致させる
- `criterion`: 判定した基準の ID。`glossary.json` の `criteria` にある ID を使う

位置は、定義の原文に含まれる文字列 (`text` の `value`) を、文書の順に連結した文字列の中で数えます。段落やリストの項目の境界にも、区切り文字は入れません。数える単位は Unicode のコードポイントで、先頭を 0 とします。`end` の位置の文字は範囲に含めないため、`start` は `end` より小さくします。たとえば、原文が `A ` と、強調された `subscriber` の 2 つの文字列から成る場合、`subscriber` の位置は `start` が 2、`end` が 12 です。

原文中の参照箇所は、参照先へのリンクとして表示します。そのため、参照の範囲には次の制約があります。

- 範囲は、1 つの段落に収める
- 1 つの定義の中で、参照の範囲を重ねない。ただし、一方の `end` と他方の `start` が同じ、接している範囲は重なりとみなさない
- 原文のリンクとは重ねないか、リンク全体と範囲を一致させる。リンク全体と一致する場合は、原文のリンクの代わりに、参照先へのリンクとして表示する

## スラッグ

用語のスラッグは、見出しから次の手順で作ります。

1. Unicode の NFKC で正規化する
2. 小文字にする
3. a 〜 z と 0 〜 9 以外の文字の並びを、ハイフン 1 つに置き換える
4. 先頭と末尾のハイフンを取り除く

たとえば、`Authentication Assurance Level (AAL)` のスラッグは `authentication-assurance-level-aal` です。用語のファイル名は、スラッグに `.json` を付けたものにします。

見出しから作ったスラッグが空になる場合 (英数字を含まない見出しなど) や、同じ用語集の別の用語のスラッグと重なる場合 (大文字と小文字だけが異なる見出しなど) に限って、用語のファイルの `slug` にスラッグを記録します。記録するスラッグは ID の形式に従い、同じ用語集の別の用語のスラッグと重ならないようにします。重なる場合は、原典で後に掲載されている用語に、見出しから作ったスラッグの末尾に `-2`・`-3` のような番号を付けたものを記録します。`slug` を記録した用語では、`slug` の値をスラッグとして使います。

## ハッシュ値

訳文に記録するハッシュ値は、SHA-256 の値を小文字の 16 進数で表した文字列です。

- 見出しの訳文: 見出しの文字列を UTF-8 で符号化したもののハッシュ値
- 定義の訳文: 定義の原文 (`source`) を [RFC 8785 (JSON Canonicalization Scheme)](https://www.rfc-editor.org/rfc/rfc8785) に従って JSON に変換し、UTF-8 で符号化したもののハッシュ値

RFC 8785 では、オブジェクトのキーを UTF-16 のコード単位の順に並べ、空白を入れません。文字列は ECMAScript の `JSON.stringify` と同じ規則で変換するため、ASCII 以外の文字はエスケープしません。

原文や見出しを修正するとハッシュ値が変わるため、検証で古い訳文として検出されます。訳文を見直したうえで、検証が示すハッシュ値に更新してください。

## 検証

次のコマンドで、`glossaries/` にあるすべての用語集を検証します。`npm run build` も、最初にこの検証を実行します。`glossaries/` がない場合は、用語集がないものとして検証を終えます。

```sh
npm run validate
```

引数で、`glossaries/` の代わりに検証するディレクトリを指定できます。指定したディレクトリがない場合は、検証は失敗します。

```sh
npm run validate -- tests/fixtures/glossaries
```

検証では、JSON Schema に従っていることに加えて、次の規則を確かめます。問題があれば、ファイルごとに内容を表示し、0 以外の終了コードで終わります。

- `glossary.json` と用語のファイルが JSON として読めること
- `terms/` に 1 つ以上の用語のファイルがあり、用語のファイル以外がないこと
- 用語集の ID がディレクトリ名と同じで、基準の ID が重複していないこと
- 原典の公開日と取得日が、暦の上で存在する日付であること
- 用語のファイル名がスラッグと一致し、スラッグが同じ用語集の別の用語と重なっていないこと
- `slug` を、見出しから作ったスラッグを使えない場合に限って記録していること
- 見出しと定義の訳文に記録されたハッシュ値が、現在の見出しと原文のハッシュ値と一致すること
- 定義の原文と訳文に、空白以外の文字があること
- 原典の URL、原典の該当箇所の URL、リンクの URL が、許可された形式の URL であること
- 参照元の定義・参照先の用語・判定した基準が存在すること
- 参照の位置が原文の範囲内にあり、その位置の文字列が記録された表現と一致すること
- 参照の範囲が 1 つの段落に収まり、原文のリンクと一部だけ重なっていないこと
- 1 つの定義の中で、参照の範囲が重なっていないこと
