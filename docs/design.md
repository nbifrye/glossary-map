## この文書について

この文書は、[要件定義書](https://github.com/nbifrye/glossary-map/blob/5d2f6d226dd5248d83e54175e13fa3f8fb587a51/docs/requirements.md) を満たすための設計を定めます。技術スタック・中間形式・グラフの計算・画面構成・安全性・アクセシビリティ・性能の目標値・テスト・実装の進め方を扱います。中間形式の項目の詳細な定義は、実装時に JSON Schema と仕様書として別に作成します。

## 全体の構成

サイトは、ビルド時にすべての計算を済ませた静的ファイルだけで構成します。ビルドは次の順に進めます。

1. リポジトリ内の中間形式のデータを読み込み、検証する。検証に失敗した場合は、ビルドを中止する
2. 用語集ごとに参照のグラフを作り、クラスタリングと配置をすべての組み合わせについて計算する
3. 用語集と用語ごとに HTML のページを生成し、グラフの描画に使うデータを JSON として出力する
4. GitHub Actions で、生成したファイルを GitHub Pages に公開する

閲覧時のブラウザーは、ビルド時に計算された結果を読み込んで描画するだけで、クラスタリングや配置の計算は行いません。計算を事前に済ませておくことで、次の 3 つの要件を同時に満たせます。

- 同じデータと同じ URL からは、常に同じ分類と配置を再現できる。ブラウザーごとの浮動小数点演算の違いの影響も受けない
- 計算中に画面の操作が妨げられることがない
- 閲覧時に外部の API を使わない

この方式では、閲覧者がアルゴリズムの計算条件を変えて再計算することはできません。要件はアルゴリズムの切り替えだけを求めているため、計算条件の変更は扱いません。

## 技術スタック

言語は TypeScript とし、実行環境には Node.js の LTS である 26 系を使います。各パッケージのバージョンは、実装時に固定します。

### サイトの生成

静的サイトの生成には [Astro](https://astro.build/) を使います。選んだ理由は次のとおりです。

- 用語ごとのページをビルド時に HTML として生成できる。JavaScript が動く前から定義と参照を読めるため、初回表示が速く、スクリーンリーダーでも読みやすい
- 用語ごとに実在するページがあるため、URL への直接アクセスに対応するための仕組みを GitHub Pages 上に用意する必要がない
- 既定では JavaScript を出力せず、グラフや検索など必要な部分だけにスクリプトを読み込める
- `security.csp` の設定で、Content Security Policy を `<meta>` 要素として出力できる。GitHub Pages では HTTP ヘッダーを設定できないため、この方式が必要になる

Vite で単一ページアプリケーションとして作る方式も比較しました。この方式では、用語の URL に直接アクセスしたときに表示するための工夫が GitHub Pages 上で必要になり、JavaScript が動くまで定義を読めないため、採用しません。

画面の部品には UI フレームワークを使わず、HTML と CSS の標準機能と、少量の TypeScript で作ります。ダイアログには `<dialog>` 要素、補足の表示には Popover API、画面幅への対応にはコンテナクエリーを使うなど、[Modern Web Guidance](https://developer.chrome.com/blog/modern-web-guidance-v1?hl=ja) が推奨する標準機能を優先します。

### グラフの描画

グラフの描画には [sigma.js](https://www.sigmajs.org/) を、グラフのデータ構造には [Graphology](https://graphology.github.io/) を使います。sigma.js は WebGL で描画し、数千のノードと辺を描画する用途を想定して作られているため、約 2,000 語と約 10,000 件の参照という要件の規模に合います。どちらも MIT ライセンスです。

Cytoscape.js も比較しました。機能は豊富ですが、標準の描画は Canvas 2D です。要件の規模で円滑に操作できるかどうかは、sigma.js の方が見込みが高いと判断しました。

### クラスタリングと配置

クラスタリングには、次の 2 つのアルゴリズムを用意します。どちらも、参照の向きを無視した無向グラフとして扱い、同じ 2 つの用語の間の参照の数を辺の重みとします。

- Louvain 法: モジュラリティを最大化する代表的な手法です。[graphology-communities-louvain](https://www.npmjs.com/package/graphology-communities-louvain) を使います
- Leiden 法: Louvain 法を改良し、用語群の内部が必ずつながっていることを保証する手法です。[networkanalysis-ts](https://www.npmjs.com/package/networkanalysis-ts) を使います

参照の向きを考慮する Infomap も候補にしました。しかし、JavaScript から使える公式実装 ([@mapequation/infomap](https://www.npmjs.com/package/@mapequation/infomap)) のライセンスは GPL-3.0-or-later です。このライセンスはリポジトリ全体のライセンスに影響するため、採用しません。

配置には、次の 2 つのアルゴリズムを用意します。

- ForceAtlas2: 参照でつながった用語どうしを近づけ、全体の構造を示す力学的な配置です。[graphology-layout-forceatlas2](https://www.npmjs.com/package/graphology-layout-forceatlas2) を使います
- 用語群別の配置: 選択したクラスタリングの結果に従って用語群ごとに領域を割り当て、その領域の中で ForceAtlas2 を適用します。用語群のまとまりを識別しやすくするための配置です

用語群別の配置はクラスタリングの結果を使いますが、クラスタリングと配置はそれぞれ独立して選択できます。2 つのクラスタリングと 2 つの配置を組み合わせた 4 通りの結果を、ビルド時に計算します。

### 検証とテスト

中間形式は JSON で保持し、JSON Schema で形式を定義します。形式の検証には [Ajv](https://ajv.js.org/) を使い、JSON Schema では表せない整合性の検証は TypeScript で実装します。単体テストには Vitest を、ブラウザーでのテストには Playwright を、アクセシビリティの自動検査には axe-core を使います。lint と format には Biome を使います。

## 中間形式

### ファイルの構成

用語集ごとにディレクトリを作り、用語ごとに 1 つの JSON ファイルを置きます。用語ごとにファイルを分けることで、プルリクエストで訳文を査読するときに差分を読みやすくします。

```text
glossaries/
  sp800-63-4/
    glossary.json
    terms/
      authenticator.json
      ...
```

`glossary.json` には、用語集の名前、原典の書誌情報 (名称・バージョン・公開日・URL・取得日)、著作権表示、ライセンス、参照と判定する基準の一覧を記録します。基準ごとに ID と説明を持たせ、各参照からは基準の ID で参照します。用語集をまたぐ参照を将来追加できるように、用語集にも一意の ID を持たせます。

### 用語と定義

用語のファイルには、見出し・見出しの訳文・定義の一覧・参照の一覧を記録します。1 つの見出しに複数の定義が掲載されている場合に備えて、定義は配列にします。各定義には、原典の該当箇所へのリンクか、リンクがない場合の記載位置 (章・ページ番号など) を記録します。

定義の原文と訳文は、許可した構造だけを持つ木構造で表します。ブロックは段落とリスト (番号付き・番号なし)、インラインは文字列・強調・リンクに限ります。HTML の文字列は保持しません。

### 用語の URL

用語の URL には、見出しから決まった規則で作るスラッグを使います。見出しを Unicode の NFKC で正規化して小文字にし、英数字以外の文字の並びをハイフン 1 つに置き換え、先頭と末尾のハイフンを取り除きます。スラッグはファイル名にもなるため、見出しが変わらない限り URL も変わりません。同じ用語集の中でスラッグが重複した場合は、検証で失敗とし、取り込みの段階で解決します。

### 参照と根拠

参照は、定義の原文とは別に、用語のファイルの参照の一覧に記録します。各参照には、参照元の定義、参照先の用語のスラッグ、根拠となる原文中の表現とその位置、判定した基準の ID を記録します。位置は、定義の原文から構造を除いた文字列の中での開始位置と終了位置とし、Unicode のコードポイント単位で数えます。参照先は、将来の拡張に備えて、用語集の ID とスラッグの組で表せる形式にします。最初のバージョンでは、同じ用語集の中の用語だけを参照先にできます。

### 訳文と原文の対応

各訳文には、対応する原文のハッシュ値を記録します。ハッシュ値は、原文の木構造を決まった規則で JSON に変換した文字列の SHA-256 とします。原文を修正してハッシュ値が変わると、古い訳文として検証で検出できます。

### 検証の内容

ビルドの最初に、次の点を検証します。1 つでも失敗した場合は、ビルドを中止します。

- JSON Schema に従っていること
- スラッグが規則どおりで、ファイル名と一致し、用語集の中で重複していないこと
- 参照先の用語が存在すること
- 根拠の位置にある原文の文字列が、記録された表現と一致すること
- 参照が、用語集に定義された基準の ID を使っていること
- すべての見出しと定義に訳文があり、訳文に記録された原文のハッシュ値が現在の原文と一致すること
- リンクの URL が `https:`・`http:` またはサイト内の相対 URL であること

検証ツールはコマンドとして単独でも実行でき、AI エージェントが取り込みの途中で結果を確認できるようにします。

## グラフの計算

用語集ごとに、用語をノード、参照を辺とする有向グラフを作ります。同じ用語から同じ用語への参照が複数ある場合は、1 本の辺にまとめ、辺にはまとめたすべての参照を対応付けます。自分自身への参照は、グラフの辺にはせず、詳細の一覧にだけ表示します。

クラスタリングと配置の乱数には、決まった値で初期化した疑似乱数生成器を使い、ノードは常にスラッグの順に処理します。ForceAtlas2 の反復回数も固定し、時間ではなく回数で計算を打ち切ります。これにより、同じデータからは常に同じ結果が得られます。

周辺グラフは、選択した用語と、その参照先と参照元の用語から成る部分グラフです。用語群は全体グラフで計算した結果をそのまま使い、全体グラフと周辺グラフで用語群の区別が変わらないようにします。配置は、部分グラフに対して選択した配置アルゴリズムを適用し、ビルド時に用語ごとに 4 通りすべてを計算します。計算した配置は用語ごとの JSON に出力し、その用語のページを開いたときにだけ読み込みます。

## 画面構成

### ページと URL

サイトには次のページを用意します。

- トップページ (`/`): 収録している用語集の一覧を表示する
- 用語集のページ (`/<用語集の ID>/`): 全体グラフ、用語の一覧、用語群の一覧、原典の書誌情報、参照と判定する基準の説明を表示する
- 用語のページ (`/<用語集の ID>/terms/<スラッグ>/`): 用語の詳細と、全体グラフまたは周辺グラフを表示する

表示モードとアルゴリズムは、クエリーパラメーター (`view`・`cluster`・`layout`) で表します。パラメーターを省略した場合は、既定値を使います。用語を選んだり表示モードを切り替えたりすると、History API で URL を更新し、ページ全体を読み込み直さずに表示を切り替えます。ブラウザーの「戻る」「進む」では、URL から表示を復元します。ドラッグで動かしたノードの位置は、ページを読み込み直すまでの間だけ保持し、URL には含めません。

### 画面の配置

用語集のページと用語のページは、ヘッダー、グラフの領域、詳細の領域の 3 つで構成します。

- ヘッダー: サイト名・用語集の切り替え・検索欄を置く
- グラフの領域: グラフ、表示モードとアルゴリズムの切り替え、凡例を置く。凡例の近くに、参照は概念の依存関係や学習順序を示さないこと、用語群は自動的に算出した結果で原典の公式な分類ではないことを表示する
- 詳細の領域: 用語のページでは、見出しとその訳文、定義の原文と訳文、原典へのリンクまたは記載位置、参照先と参照元の一覧、各参照の根拠を表示する。用語集のページでは、用語の一覧と用語群の一覧を表示する

定義の原文中の参照箇所はリンクとして表示し、選ぶと参照先の用語へ移動します。グラフ上の線を選ぶと、その線にまとめたすべての参照の根拠を詳細の領域に表示します。

広い画面では、グラフの領域と詳細の領域を左右に並べます。狭い画面では縦に並べ、グラフの領域は周辺グラフだけを表示します。全体グラフの操作は、狭い画面では提供しません。

### 検索

検索欄では、見出しと見出しの訳文を対象に、部分一致で用語を探します。入力と見出しは、どちらも NFKC で正規化し、大文字と小文字を区別せずに比較します。検索に使う索引はビルド時に用語集ごとに作成します。検索欄は、WAI-ARIA の combobox パターンに従い、キーボードで候補を選べるようにします。

## 安全性

原文と訳文は、中間形式の木構造から DOM を組み立てて描画します。文字列は常にテキストとして扱い、HTML として解釈しません。リンクの URL は検証の段階で制限し、描画の段階でも `https:`・`http:`・サイト内の相対 URL 以外は描画しません。

Content Security Policy は、Astro の `security.csp` の設定で `<meta>` 要素として出力し、スクリプトとスタイルの読み込み元を自サイトに限ります。フォントにはシステムフォントを使い、外部のフォントや CDN は使いません。

## アクセシビリティ

グラフの操作を除く画面全体で、WCAG 2.1 AA を満たすようにします。グラフに表示する用語・参照・所属する用語群は、詳細の領域の一覧からも確認できます。グラフの領域には、一覧の場所を示す説明を付けます。

用語群は色だけでなく、一覧での用語群の名前でも区別できるようにします。`prefers-reduced-motion` が設定されている場合は、グラフの移動や拡大・縮小のアニメーションを省きます。

## 性能の目標値

性能の目標値を、次のように定めます。計測には、約 2,000 語と約 10,000 件の参照を持つ試験用の用語集を自動で生成して使います。計測する環境は、GitHub Actions の標準の Linux ランナー上の Chromium とします。

- 初回表示: 用語のページの Largest Contentful Paint が 2.5 秒以内であること
- 全体グラフの表示: ページの読み込みを始めてから、全体グラフを操作できるようになるまでが 3 秒以内であること
- 操作時の応答性: 拡大・縮小・平行移動・ノードの選択の間に、50 ミリ秒を超えるメインスレッドのタスクが発生しないこと。用語の選択や表示の切り替えの Interaction to Next Paint が 200 ミリ秒以内であること
- 計算時間: 1 つの用語集のクラスタリングと配置の計算が、ビルド時に 60 秒以内に終わること
- データ量: 1 つの用語集のグラフのデータが、gzip で圧縮して 1 MB 以内であること

閲覧時にはクラスタリングと配置の計算を行わないため、閲覧時の計算時間の目標値は定めません。

## テストと CI

プルリクエストごとに、GitHub Actions で次のチェックを実行します。

- Biome による lint と format の確認
- TypeScript の型検査
- Vitest による単体テスト。中間形式の検証、スラッグの規則、ハッシュ値、同じデータから同じ分類と配置が得られることを確認する
- 中間形式の検証とビルド
- Playwright によるブラウザーでのテスト。Chromium・Firefox・WebKit で、検索・定義の閲覧・参照の移動・グラフの操作・URL からの復元を確認する。axe-core によるアクセシビリティの自動検査と、性能の目標値の計測も行う

`main` ブランチへの push では、チェックに成功したビルドの結果を GitHub Pages に公開します。

## 実装の進め方

実装は、次の順にプルリクエストを分けて進めます。

1. 開発環境の整備: Astro・TypeScript・Biome・Vitest・Playwright・CI・GitHub Pages への公開を設定し、Modern Web Guidance を導入する
2. 中間形式の仕様・JSON Schema・検証ツール
3. AI エージェント向けの取り込み手順と、SP 800-63-4 の用語集の取り込み
4. 用語集のページと用語のページ、検索
5. グラフの描画と操作、全体グラフと周辺グラフの切り替え、URL による状態の共有
6. クラスタリングと配置の計算と切り替え
7. 性能の計測と試験用の用語集
8. SP 800-63A-4・SP 800-63B-4・SP 800-63C-4 の用語集の取り込み
